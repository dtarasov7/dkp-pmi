# Пункт 53

Отображения действия политик (NetworkPolicy) в веб-интерфейсе. Только для кластеров с CNI Cilium

## Перед запуском

По информации владельца стенда Cilium уже используется, Hubble включён.
Дополнительно включать или устанавливать их не требуется.
`01-prepare.sh` покажет опубликованные Ingress-адреса в `d8-cni-cilium`, затем
создаст тестовые Pod. Откройте Hubble UI по соответствующему адресу или через меню
платформы под своей учётной записью.

Реальную доступность трафика до запрета и его блокировку после NetworkPolicy
проверит `02-check.sh`. Если исходный запрос не проходит, скрипт завершится
с ошибкой: сначала нужно устранить существующий сетевой запрет для тестовых Pod.

## Демонстрация

1. Подготовьте Pod. В Hubble UI выберите namespace pmi-53, текущее время и оба Pod.
2. Запустите проверку: до политики HTTP даёт `pmi-ok`, после — тайм-аут.
   Скрипт повторяет запрос, пока правило применяется, и останавливается при первом
   отказе. HTTP readinessProbe подтверждает готовность nginx.
3. В таблице потоков покажите client → server:8080/TCP, сначала FORWARDED,
   затем DROPPED с причиной POLICY_DENIED (название зависит от версии UI).
   Сопоставьте адреса с `kubectl -n pmi-53 get pods -o wide` и селектором
   `kubectl -n pmi-53 get networkpolicy deny-server -o yaml`.
4. Сохраните снимок UI с временем, адресами и verdict. Если UI не показывает причину,
   подтвердите её Hubble CLI/журналом Cilium того же потока и зафиксируйте ограничение UI.

Для запрещённого запроса принимается только код завершения curl `28`
(тайм-аут). Текст ошибки выводится, но его язык не влияет на проверку.
Ошибки подключения `7`, HTTP-ошибки `22` и ошибки kubectl/RBAC не засчитываются.
В коде одна последовательность: успешный запрос → создание политики → запрос
с тайм-аутом → проверка готовности сервера. Цикл ограничен десятью попытками;
он нужен только для ожидания применения правила Cilium. `CURL_STATUS` хранит
код последнего запроса; конструкция `|| CURL_STATUS=$?` сохраняет код ошибки
и позволяет проверить ожидаемый отказ, не прерывая скрипт немедленно.

Критерий: **в веб-интерфейсе** видны разрешённые и запрещённые потоки соответствующих
Pod. Один тайм-аут или список YAML-политик не закрывает пункт. Политика остаётся
до очистки, чтобы комиссия успела осмотреть интерфейс.

Источники: [Hubble UI](https://docs.cilium.io/en/stable/observability/hubble/hubble-ui/),
[сетевые политики Deckhouse](https://deckhouse.io/products/kubernetes-platform/documentation/v1/admin/configuration/network/policy/configuration.html).


## Тестовые образы

HTTP-сервер — имеющийся `nginx`, клиент — `redos_sudo` с curl.
Для обоих задано `imagePullPolicy: IfNotPresent`.
Nginx слушает 8080, возвращает `pmi-ok` и запускается от UID 1000 с собственными
конфигурацией, PID и временными файлами в `/tmp/pmi-nginx`.
Утилиты curl/wget внутри nginx не требуются. HTTP readinessProbe проверяет ответ
сервера, а `kubectl wait` проверяет готовность Pod после сетевого отказа.
Запросы клиента используют curl с `--noproxy '*'`, чтобы обращаться прямо
к проверяемому Pod/сервису.

## Запуск

После задания внешних параметров, если они перечислены выше, из каталога `53`:

```bash
bash 01-prepare.sh
bash 02-check.sh
# После фиксации результатов, в том числе при неудаче проверки:
bash 03-cleanup.sh
```

`01-prepare.sh` создаёт тестовые ресурсы; `02-check.sh` выполняет проверки;
`03-cleanup.sh` удаляет только ресурсы этого испытания. Скрипты запускаются независимо.
Повторный полный прогон выполняйте после очистки.

Общие условия и ограничения версии: [README комплекта](../README.md).
