# Пункт 34

Аудит событий Kubernetes API

## Предпосылки и демонстрация

`01-prepare.sh` сам найдёт API-серверы и проверит, что каждый запущен
с файлом политики аудита и выходом аудита в файл/stdout либо webhook.
Если этих настроек нет, подготовка завершится до создания тестовых объектов.

Запускайте с административным kubeconfig. Запрос `--as` выполняется от имени
тестовой учётной записи — это impersonation. Для анализа выгрузки нужен `jq`.

В журнале должны сохраняться операции create/get/patch/delete ConfigMap
в тестовом namespace и отказ 403: уровень не ниже `Metadata` (пользователь,
объект, действие, результат), стадия `ResponseComplete` (запрос обработан).
Полноту записей автоматически проверит `02-check.sh` после предоставления
выгрузки. Само наличие флагов аудита не гарантирует, что политика записывает
все эти действия: например, базовая политика может исключать чтение.
Аудит API и `kubectl get events` — разные источники, для этого теста нужна выгрузка аудита.

1. Покажите `kubectl -n kube-system get pods -l component=kube-apiserver -o yaml`:
   аргументы `--audit-policy-file`, `--audit-log-path`, тома и путь на узле.
   Эти аргументы также покажет и проверит скрипт подготовки.
2. Выполните подготовку. Запишите UTC-время начала/конца и текущего пользователя.
3. Через существующий сборщик журналов экспортируйте события **со всех master-узлов**
   за это окно в JSON Lines: одна исходная запись audit.k8s.io/Event в строке,
   без оболочки Loki/syslog. Либо прочитайте соответствующие файлы на master-узлах
   по пути из аргументов API-сервера, включая ротацию. Не выгружайте содержимое Secret.
4. Укажите `export AUDIT_FILE=/путь/к/выгрузке.jsonl` и запустите проверку.
   Фильтр по namespace в скрипте дополняет, но не заменяет фильтр по времени экспорта.
5. Сохраните auditID, время, пользователя (при impersonation также impersonatedUser),
   verb, objectRef, responseStatus и решение authorization.k8s.io/decision.

## Ожидаемый результат

Видны успешные четыре операции с маркером и get с кодом 403 от observer.
Отсутствие события означает неполную настройку/выгрузку аудита, а не успешное испытание.
Журналы сохраняются как доказательства, очистка их не удаляет.

Основание: [аудит Kubernetes](https://kubernetes.io/docs/tasks/debug/debug-cluster/audit/).

## Запуск

После задания внешних параметров, если они перечислены выше, из каталога `34`:

```bash
bash 01-prepare.sh
bash 02-check.sh
# После фиксации результатов, в том числе при неудаче проверки:
bash 03-cleanup.sh
```

`01-prepare.sh` создаёт тестовые ресурсы; `02-check.sh` выполняет проверки;
`03-cleanup.sh` удаляет только ресурсы этого испытания. Скрипты запускаются независимо.
Повторный полный прогон выполняйте после очистки.

Общие условия и ограничения версии: [README комплекта](../README.md).
