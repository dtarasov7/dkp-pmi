и 36 самостоятельных скриптов. Пункты 55, 75 и 76 не создают объектов.
Исходные `spisok.csv`, `bash.md` и `AGENTS.md` не изменялись.

Выполнено локально:

- `bash -n` для всех 36 скриптов, включая дополненные проверки подготовки: ошибок нет.
- ShellCheck для всех 36 скриптов: ошибок и предупреждений нет.
- Разбор 16 встроенных YAML-блоков: 38 объектов; дополнительно разобраны
  3 объекта внутри resourcesTemplate ProjectTemplate после подстановки маркера.
  Для переменных окружения использованы тестовые DNS-имена/значения.
- Проверены структура комплектов, UTF-8 без CRLF, завершающий LF,
  локальные ссылки README, порядок создания и ссылки roleRef.
- Проверены имена, селекторы и зависимости Service/Pod, CSI/SecretsStoreImport,
  Project/ProjectTemplate, RBAC и маршрута log-shipper; очистка адресует только
  имена теста. Тестовые namespace должны быть свободны до запуска.
- 10 локальных прогонов на искусственных ответах: матрица Gatekeeper проходит
  с ожидаемыми ответами; неожиданное разрешение, RBAC Forbidden и сетевой сбой
  приводят к ошибке. Для обоих сценариев аудита полный набор событий принимается,
  отсутствие delete или ожидаемого 403 — отвергается.

Повторная базовая проверка из корня:

```bash
for script in [0-9]*/*.sh; do
  bash -n "$script" || exit 1
done
shellcheck [0-9]*/*.sh
python -m unittest discover -s tests -v
```

Это статическая проверка и локальная проверка обработки ответов, **не прогон
на Deckhouse**. Полная валидация манифестов против CRD/OpenAPI CSE 1.73.4,
доступность образов, синхронизация контроллеров, интерфейсы, внешние сервисы
и фактическое исполнение политик требуют испытательного стенда.
Публичная документация части модулей относится к более новым выпускам;
такие места явно отмечены в README пунктов.

Проверка доступности текущего контекста `kind-ktop-test`:

```text
kubectl --request-timeout=5s -n d8-system get deployment deckhouse ...
The connection to the server 127.0.0.1:35865 was refused
```

Изменений в Kubernetes не выполнялось. Для прогона используйте доступный
испытательный CSE 1.73.4 и его kubeconfig. Пример команды после подготовки
предпосылок и подстановки настоящего пути:

```bash
KUBECONFIG=/путь/к/cse-kubeconfig bash 01-prepare.sh
```

Результат приёмки фиксируйте отдельно по каждому пункту с доказательствами,
а не по наличию файлов или одному сообщению «УСПЕХ».

## Автоматические проверки условий запуска

После уточнения владельца стенда Cilium и Hubble считаются уже включёнными.
В README пунктов описано, какие условия проверяет скрипт и какие внешние данные
должен указать оператор. Проверки модулей и используемых полей API перенесены
в `01-prepare.sh` пунктов 5, 36, 37, 41, 48 и 51. Пункт 54 проверяет модуль
и наличие webhook Gatekeeper. Пункты 34 и 56 проверяют аргументы аудита всех
найденных API-серверов. Пункт 58 проверяет CLI Velero и доступность записи
в выбранный BackupStorageLocation. До успешного завершения этих проверок
тестовые объекты не создаются.

В `tests/test_prepare_preconditions.py` сохранены четыре автоматических теста
с 41 контрольным случаем. Используются локальные подставные ответы kubectl/velero,
без обращений к кластеру. Проверено:

- подходящие ответы позволяют дойти до первой команды создания;
- отсутствующий или неготовый модуль останавливает подготовку;
- отсутствие каждого из шести требуемых полей Project/ProjectTemplate приводит
  к остановке; запрашивается именно нужная версия API;
- отсутствие CSI, Syslog-кодека, Pod etcd, webhook Gatekeeper или аргументов аудита
  на одном из API-серверов обнаруживается до мутаций;
- недоступное/доступное только на чтение хранилище Velero, отсутствие CLI,
  отсутствие нужного Ingress-контроллера или выключенный sidecar также останавливают
  подготовку до мутаций.

Все четыре теста и 41 контрольный случай прошли успешно. После изменений повторно
прошли Bash, ShellCheck, разбор YAML, проверка локальных ссылок и UTF-8/LF.
Это не подтверждает состояние реального стенда; доступ к CSE 1.73.4 не появился.

## Vault на отдельном сервере РЕД ОС 7.3

Инструкция `5/VAULT-REDOS-7.3.md` адаптирована к двум машинам: сервер Vault
без kubectl и рабочая машина с kubectl и скриптами пункта 5. Используется
актуальный пакет из уже настроенных репозиториев. Выбор/настройка репозиториев,
настройка firewall и проверки версии Vault исключены.

Для Kubernetes auth используется URL API через Ingress Deckhouse и соответствующий
CA из kubeconfig. Если kubeconfig использует системное доверие, на сервере Vault
берётся системный набор CA РЕД ОС. Адреса master-узлов и kube-root-ca.crt
в этой инструкции не используются. Добавлен фактический POST TokenReview
с проверкой authenticated перед настройкой Vault.

Проверены 11 блоков команд через bash -n и ShellCheck отдельно для терминала
запуска Vault, терминала его настройки и рабочей машины — ошибок нет.
Проверено отсутствие вызовов kubectl в блоках сервера Vault.
На искусственных данных выполнены jq-фильтры создания TokenReview, ModuleConfig,
merge patch и JSON Patch восстановления. Проверены ссылки и UTF-8/LF.
Команды на реальном сервере РЕД ОС, Vault и Deckhouse не выполнялись.
