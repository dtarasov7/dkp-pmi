# Пункт 21

Платформа обеспечивает соблюдение указанных в манифестах развёртываний значений
CPU, RAM, replicas и других параметров ресурсов.

## Что создаётся и проверяется

Все объекты находятся в отдельном namespace `pmi-21`.

| Параметр | Значение | Подтверждение |
|---|---|---|
| Deployment replicas | Сначала 2, затем 3 и 1 | После scale и rollout status число реплик в статусе Deployment совпадает с заданным; список Pod показывается комиссии |
| requests.cpu / requests.memory | 50m / 32Mi на контейнер | Проверяются реальные спецификации Pod после каждой смены числа реплик |
| limits.cpu | 100m на контейнер | Квота cgroup равна 0,1 CPU; при нагрузке растёт nr_throttled |
| limits.memory | 64Mi на контейнер | Лимит cgroup равен 64Mi; 16 MiB выделяются, попытка выделить 256 MiB завершается OOMKilled |

`requests` определяют потребности для планирования, `limits` — ограничения
контейнера. `100m` означает 0,1 CPU, `64Mi` — 64 × 1024 × 1024 байт.
Число реплик задаётся отдельно в `Deployment.spec.replicas`.

## Перед запуском

Скрипты выполняются на рабочей машине с `kubectl` и административным
kubeconfig. В namespace `pmi-21` должны быть разрешены `kubectl exec` и создание
Deployment/Job с указанными ресурсами. Проверяется стандартный Kubernetes API;
отдельный модуль Deckhouse включать не требуется.

В обоих манифестах используется имеющийся образ `redos_sudo` со `stress-ng`
и Python 3. Обычный контейнер выполняет `sleep`, CPU нагружает `stress-ng`.
Две короткие команды `python3` выделяют память; алиас `python` не требуется.
Указано `imagePullPolicy: IfNotPresent`. При другом имени в registry замените
`image` в `01-prepare.sh` и `02-check.sh`. На узле должны быть доступны счётчики
cgroup: поддержаны стандартные размещения файлов CPU для cgroup v1 и v2.

Нагрузка CPU длится примерно 15 секунд внутри одного контейнера с лимитом 100m:

```bash
stress-ng --cpu 1 --cpu-method loop --timeout 15s --metrics-brief
```

`--cpu 1` запускает один вычислительный процесс, `--cpu-method loop` выбирает
простую вычислительную нагрузку, `--timeout` ограничивает время,
`--metrics-brief` выводит краткий отчёт.

Проверка памяти выполняется отдельным Job с лимитом 64Mi, без повторных запусков.
При необходимости Job ограничен 120 секундами исполнения. Если скрипт сообщает,
что throttling не зафиксирован, проверьте доступность CPU на выбранном узле:
при сильной конкуренции процесс может не получить достаточно CPU даже для
достижения своей квоты. Такой результат не объявляется успешной проверкой.

## Запуск

Из каталога `21`:

```bash
bash 01-prepare.sh
bash 02-check.sh
# После сохранения результатов, в том числе при ошибке проверки:
bash 03-cleanup.sh
```

- `01-prepare.sh` создаёт Deployment с двумя репликами и ждёт их готовности.
- `02-check.sh` изменяет replicas, сравнивает ресурсы реальных Pod с манифестом,
  нагружает CPU и проверяет ожидаемое завершение отдельного Job по памяти.
- `03-cleanup.sh` удаляет только namespace `pmi-21` и созданные в нём ресурсы.

`02-check.sh` запускается один раз на подготовленном окружении. Для повторного
полного прогона выполните очистку и подготовку: после проверки остаются одна
реплика Deployment и завершённый Job, чтобы комиссия могла их осмотреть.

## Ожидаемый результат и доказательства

1. После каждого `scale` команда `rollout status` подтверждает готовность,
   а `wait` — заданное число реплик в статусе Deployment. В списке Pod при уменьшении
   числа реплик могут временно отображаться удаляемые Pod (`Terminating`).
   Ресурсы контейнера `app` во всех показанных репликах соответствуют манифесту.
2. При нагрузке `stress-ng` квота CPU равна 100m, счётчик `nr_throttled`
   увеличивается. Этот счётчик показывает, сколько раз cgroup приостанавливала
   вычисления из-за исчерпания квоты. Скрипт выводит значения до и после нагрузки.
   Квота — разрешённое время CPU за один период: 10000/100000 означает 0,1 CPU.
   Само чтение поля limits без роста счётчика не засчитывается.
3. В логах Job показан лимит cgroup 67108864 байт, сообщение об успешном
   выделении 16 MiB, затем попытка
   выделить 256 MiB. В статусе именно контейнера `memory` указан `OOMKilled`,
   exitCode=137, а фактический лимит Pod — 64Mi. Обычный выход 137, MemoryError,
   ошибка образа, Evicted или истечение activeDeadlineSeconds не засчитываются.
4. После этого обычный Deployment продолжает работать с одной готовой репликой.
   Сохраните вывод скрипта, спецификации Pod, результаты CPU и статус завершения Job.

Преднамеренно неуспешный Job здесь является ожидаемым результатом проверки
ограничения памяти. Скрипт завершится успешно только после проверки причины.
Для превышения памяти используется `exec python3 -c 'memory = bytearray(256 * 1024 * 1024)'`:
`bytearray` выделяет и заполняет нулями 256 MiB, а `exec` заменяет процесс запуска
на Python, чтобы Kubernetes зафиксировал причину его завершения.
`stress-ng` используется для CPU: при нехватке памяти он может обработать гибель
дочернего процесса, и тогда статус всего контейнера не будет `OOMKilled`.
Сценарий охватывает перечисленные CPU/RAM/requests/replicas; для иных ресурсов
(например, GPU или ephemeral-storage) требуется отдельное конкретное требование.
