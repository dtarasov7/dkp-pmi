# Пункт 37

Система предоставляет возможность блокировки изменений политик в зависимости результатов контроля, указанного в п36

## Что проверит подготовка

`01-prepare.sh` проверит готовность модуля `admission-policy-engine` и наличие
используемых полей `SecurityPolicy` версии `deckhouse.io/v1alpha1`:
режима запрета, выбора тестового namespace и разрешения hostNetwork.
Если проверка не пройдёт, тестовые объекты созданы не будут; причина появится в выводе.

Скрипты запускаются с административным kubeconfig. Они выполняют запросы от имени
тестовых ServiceAccount с помощью `--as` — это называется impersonation.
Фактические разрешения и отказы проверит `02-check.sh`.

## Что потребуется для показа аудита

Сборщик журналов должен сохранять изменения Role и SecurityPolicy:
операция `patch`, уровень аудита не ниже `Metadata`, стадия `ResponseComplete`.
Эти значения означают: записывать факт изменения с пользователем, объектом
и результатом после обработки запроса. Запись тела политики для теста не нужна.
Сохраните успешные запросы editor и отклонённые запросы observer по инструкции
[пункта 34](../34/README.md). Наличие записей проверяется после выполнения запросов;
одна доступность API не подтверждает, что сборщик их сохранил.

## Демонстрация

1. Подготовка создаёт Role и SecurityPolicy, observer без прав и editor с правами
   patch только конкретных тестовых политик. Права editor на configmaps исключают
   срабатывание отдельной защиты Kubernetes от повышения привилегий при правке Role.
2. Проверка выполняет **реальные изменения**, а не только `auth can-i`: добавляет list
   к Role и переключает allowHostNetwork в изолированной SecurityPolicy.
   Observer получает Forbidden, содержимое остаётся прежним; editor выполняет тот же patch.
3. В системе аудита за время запуска отфильтруйте resource=roles, namespace=pmi-37,
   name=target и resource=securitypolicies, name=pmi-37. Покажите две записи 403
   для observer и две успешные записи 200 для editor. Проверьте impersonatedUser,
   verb=patch, auditID, annotations.authorization.k8s.io/decision, время и объект.
   Экспорт выполняется как в [пункте 34](../34/README.md).

## Критерий приёмки

Для пункта 36 обязательны записи контроля **обоих** видов политик и идентификация
инициатора. Для пункта 37 обязательны отказ, неизменность объекта и разрешённая
контрольная операция. Сообщение скрипта подтверждает API-поведение; без просмотра
аудита пункт 36 не закрывается. Это синхронная авторизация запроса: отдельное
автоматическое блокирование по событиям SIEM этим сценарием не проверяется.
После проверки тестовая политика допускает hostNetwork, но в её namespace нет нагрузок.

Источники: [RBAC](https://kubernetes.io/docs/reference/access-authn-authz/rbac/),
[SecurityPolicy](https://deckhouse.io/modules/admission-policy-engine/cr.html).

## Запуск

После задания внешних параметров, если они перечислены выше, из каталога `37`:

```bash
bash 01-prepare.sh
bash 02-check.sh
# После фиксации результатов, в том числе при неудаче проверки:
bash 03-cleanup.sh
```

`01-prepare.sh` создаёт тестовые ресурсы; `02-check.sh` выполняет проверки;
`03-cleanup.sh` удаляет только ресурсы этого испытания. Скрипты запускаются независимо.
Повторный полный прогон выполняйте после очистки.

Общие условия и ограничения версии: [README комплекта](../README.md).
