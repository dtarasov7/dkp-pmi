# Пункт 75

Должна иметься поддержка стандартов и защищенных протоколов обмена данными по каналу передачи данных, в том числе следующих:- между компонентами Системы – :TLS (не ниже версии 1.3); - при взаимодействии с другими системами – HTTPS.

## Что требуется доказать

Наличие HTTPS и поддержка TLS 1.3 отличаются от требования **не ниже TLS 1.3**:
во втором случае сервер должен отвергать TLS 1.2 и более старые версии.
Нельзя подтвердить все каналы единственной проверкой Ingress.

## Демонстрация без изменения кластера

1. Составьте перечень реальных каналов по архитектуре стенда: клиент → API,
   API → etcd (2379), etcd peer → peer (2380), API → kubelet (10250),
   служебные webhook, Dex/OIDC, Ingress → backend, service mesh и внешние интеграции.
   Для каждого укажите источник, назначение, порт, терминатор TLS и владельца.
   Незащищённые/неприменимые каналы отразите явно с основанием.
2. Для каждого TLS endpoint выполните ниже две проверки из сети фактического
   источника. Подставьте HOST, PORT, CA_FILE и TLS_NAME (DNS SAN сертификата).
   Для IP SAN используйте `-verify_ip` вместо `-verify_hostname`.

```bash
openssl s_client -connect "$HOST:$PORT" -servername "$TLS_NAME"   -CAfile "$CA_FILE" -verify_return_error -verify_hostname "$TLS_NAME"   -tls1_3 -brief </dev/null
openssl s_client -connect "$HOST:$PORT" -servername "$TLS_NAME"   -CAfile "$CA_FILE" -verify_return_error -verify_hostname "$TLS_NAME"   -tls1_2 -brief </dev/null
```

Для mTLS добавьте в **обе** команды `-cert "$CLIENT_CERT" -key "$CLIENT_KEY"` с
разрешённым тестовым клиентским сертификатом. Рабочие ключи etcd не переносите
на посторонние машины; запускайте проверку из разрешённой административной среды.
Отсутствие клиентского сертификата может вызвать отказ обеих проб и ничего
не доказывает о минимальной версии TLS.

3. Положительная проба должна согласовать TLSv1.3 с доверенным сертификатом;
   отрицательная — завершиться именно protocol version/unsupported protocol.
   Проверьте текст согласования, а не только exit code openssl: EOF после
   успешного handshake или ошибка клиентского CA не означают запрет TLS 1.2.
4. Для HTTPS-интеграций выполните реальный запрос `curl --cacert "$CA_FILE"
   --max-time 10 "https://$TLS_NAME:$PORT/ПУТЬ_ПРОВЕРКИ"` с предусмотренной
   аутентификацией без вывода токенов. Проверьте сертификат и ответ приложения.
5. Сопоставьте пробы с эффективными параметрами компонентов (например,
   tls-min-version API, min/max TLS etcd, ssl-protocols ingress, конфигурацией Envoy).
   Не редактируйте управляемые Deckhouse static Pod манифесты для этой демонстрации.

## Критерий и протокол

Запишите по каждому каналу: адрес/порт, фактическую версию, cipher, CA/SAN,
результат TLS1.3, результат TLS1.2, конфигурацию и дату.
Любой принятый TLS1.2 на внутреннем канале — несоответствие исходному пункту.
У CSE 1.73.4 минимальная TLS1.3 **не считается гарантированной** без этой проверки
и подтверждения поддерживаемых настроек поставщиком. Метрики Kiali показывают
mTLS, но не заменяют проверку версии протокола. Шифрование etcd на диске — другой механизм.

Скрипты подготовки/очистки не нужны: проверяются существующие соединения,
объекты не создаются. Глобальное повышение минимальной TLS здесь не выполняется.
