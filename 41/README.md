# Пункт 41

Система предоставляет возможность мониторинга (проверки) на предмет наличия шифрования (TLS) соединений между подами и внешних соединений с подами с помощью Kiali при условии использования сервисной сети Istio и применении ServiceEntry для внешнего сервера

## Что проверит подготовка

До создания объектов `01-prepare.sh` проверит:

- готовность модуля Istio и поля API, используемые для настройки шифрования;
- доступность файлов сертификата и ключа;
- наличие IngressNginxController с указанным классом и включённым
  `spec.enableIstioSidecar`: без sidecar контроллер не сможет обратиться к Pod,
  принимающему только взаимно защищённые соединения Istio.

Скрипт также покажет опубликованные адреса интерфейсов Istio/Kiali.
Наличие sidecar в созданных Pod отдельно проверит `02-check.sh`.

## Какие значения задать перед запуском

| Переменная | Что указать |
|---|---|
| `APP_HOST` | Свободное тестовое DNS-имя, направленное на выбранный Ingress-контроллер |
| `EXTERNAL_HOST` | Имя внешнего HTTPS-сервера без `https://` и пути; `/` должен возвращать 2xx |
| `INGRESS_CLASS` | Значение `spec.ingressClass` выбранного IngressNginxController |
| `TLS_CERT` | Путь к PEM-сертификату для APP_HOST |
| `TLS_KEY` | Путь к соответствующему закрытому ключу |
| `TLS_CA` | Путь к CA, которому доверяется сертификат APP_HOST; нужен проверке |

Имена, сертификаты и внешний сервер предоставляет владелец стенда.
Значения задаются в том же терминале через `export ИМЯ=значение`.
Список контроллеров можно посмотреть командой
`kubectl get ingressnginxcontrollers.deckhouse.io -o yaml`.
Ключ не выводите на экран.

Внешний HTTPS-сервер должен иметь сертификат, которому доверяет контейнер curl.
Маршруты, DNS и успешный ответ проверит реальный запрос в `02-check.sh`.
В сценарии используется стандартный домен сервисов Kubernetes `cluster.local`.
Если на стенде настроен другой, замените два `server.pmi-41.svc.cluster.local`
в `01-prepare.sh` на фактическое полное имя сервиса.

## Демонстрация

1. Подготовка создаёт два Pod с sidecar, Service, STRICT PeerAuthentication,
   ISTIO_MUTUAL DestinationRule, внешний ServiceEntry и HTTPS Ingress.
2. В Kiali откройте Graph, namespace pmi-41, последние 5 минут, включите Security/mTLS
   и отображение внешних сервисов. Запустите проверку для генерации потока запросов.
3. Покажите client → server и ingress-controller → server. Для каждого ребра
   откройте признаки mTLS/долю защищённого трафика; зафиксируйте время и объём запросов.
4. Покажите EXTERNAL_HOST как ServiceEntry. HTTPS инициирует приложение, Envoy видит
   зашифрованный TCP/TLS-поток. Значок mTLS для этого ребра может отсутствовать:
   `unknown` или отсутствие замка **не доказывает plaintext**, а ServiceEntry сам
   по себе не включает шифрование. Подтвердите внешнее TLS-согласование командой
   `kubectl -n pmi-41 exec client -c app -- curl -v --max-time 10 https://ИМЯ/`
   (без авторизационных заголовков) и сертификатом сервера.
5. Входящий внешний канал проверяется curl с CA к APP_HOST; отдельно mTLS защищает
   Ingress → Pod. Один замок на внутреннем ребре не подтверждает браузер → Ingress.

Критерий: Kiali показывает фактический mTLS внутренних рёбер, внешние связи
сопоставлены с TLS-проверками и ServiceEntry. Если установленная Kiali не определяет
шифрование внешнего канала, зафиксируйте эту границу: мониторинг **всех** внешних TLS
через Kiali таким сценарием полностью не подтверждён. Версия TLS 1.3 — пункт 75.

Источники: [Istio в Deckhouse](https://deckhouse.io/modules/istio/),
[индикаторы безопасности Kiali](https://kiali.io/docs/features/security/).


## Тестовые образы

HTTP-сервер — имеющийся `nginx`, клиент — `redos_sudo` с curl.
Для обоих задано `imagePullPolicy: IfNotPresent`.
Nginx слушает 8080, возвращает `pmi-ok` и запускается от UID 1000 с собственными
конфигурацией, PID и временными файлами в `/tmp/pmi-nginx`.
Утилиты curl/wget внутри nginx не требуются. HTTP readinessProbe проверяет ответ
сервера.
Запросы клиента используют curl с `--noproxy '*'`, чтобы обращаться прямо
к проверяемому Pod/сервису.

## Запуск

После задания внешних параметров, если они перечислены выше, из каталога `41`:

```bash
bash 01-prepare.sh
bash 02-check.sh
# После фиксации результатов, в том числе при неудаче проверки:
bash 03-cleanup.sh
```

`01-prepare.sh` создаёт тестовые ресурсы; `02-check.sh` выполняет проверки;
`03-cleanup.sh` удаляет только ресурсы этого испытания. Скрипты запускаются независимо.
Повторный полный прогон выполняйте после очистки.

Общие условия и ограничения версии: [README комплекта](../README.md).
