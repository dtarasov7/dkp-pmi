# Пункт 58

Платформа обладает встроенным механизмом резервного копирования распределенной базы etcd, поддерживает стороннее решение резервного копирования, совместимое с Kubernetes.

## Часть 1. Встроенное копирование etcd — без изменений кластера

1. Покажите `kubectl get moduleconfig control-plane-manager -o yaml` и эффективные
   настройки etcd.backup по локальной документации. Отсутствие поля не означает
   отключение: необходимо учитывать значение по умолчанию установленной версии.
2. Найдите штатное задание: `kubectl -n kube-system get cronjobs,jobs`.
   Покажите YAML CronJob, расписание, последний успешный Job и его лог:
   `kubectl -n kube-system logs job/ИМЯ_УСПЕШНОГО_JOB --all-containers=true`.
3. По volumes/hostPath задания определите расположение снимка на master-узле.
   Через административную сессию покажите файл, размер, время и проверьте копию
   командой `etcdutl snapshot status ПУТЬ_К_СНИМКУ -w table` совместимой версии etcd.
   Сохраните hash/revision/total keys/size и успешный статус задания.
4. Восстановление etcd, если входит в программу, выполните только на отдельном
   восстановительном стенде по регламенту CSE 1.73.4; сравните контрольный объект
   до снимка и после восстановления. Работающий кластер этими скриптами не заменяется.

Критерий первой части: штатный механизм включён, расписание работает, получен
читаемый валидный снимок. Один успешный Velero backup не подтверждает backup etcd.

## Часть 2. Совместимое стороннее решение — три скрипта

Velero должен быть установлен в namespace `velero` и подключён к выделенному
объектному хранилищу. `01-prepare.sh` сам проверит доступность CLI `velero`,
состояние хранилища `Available` и возможность записи в него. До завершения этих
проверок namespace и резервная копия не создаются.

По умолчанию выбирается BackupStorageLocation с именем `default`.
Это объект Kubernetes, содержащий настройки подключения Velero к хранилищу.
Если на стенде он называется иначе, посмотрите
`kubectl -n velero get backupstoragelocations` и перед запуском задайте
`export BACKUP_STORAGE_LOCATION=фактическое-имя`.
Имена тестовых backup/restore `pmi-58` должны быть свободны.

Подготовка создаёт ConfigMap и резервирует только configmaps namespace pmi-58.
Проверка требует Completed, восстанавливает в pmi-58-restored и сравнивает значение.
В `velero restore describe pmi-58 --details` дополнительно проверьте отсутствие ошибок.
Это проверка Kubernetes-объекта; данные PVC и восстановление etcd Velero-сценарием
не охвачены. Для PVC нужен отдельный тест согласованности выбранного CSI/FS-backup.

Очистка удаляет и локальные ресурсы, и **свою** копию в объектном хранилище через Velero.
Очистка допускает отсутствие backup при незавершённой подготовке.
Штатные снимки etcd сохраняются.

Источники: [параметры backup etcd](https://deckhouse.io/modules/control-plane-manager/configuration.html),
[Velero backup](https://velero.io/docs/main/backup-reference/),
[Velero restore](https://velero.io/docs/main/restore-reference/).

## Запуск

После задания внешних параметров, если они перечислены выше, из каталога `58`:

```bash
bash 01-prepare.sh
bash 02-check.sh
# После фиксации результатов, в том числе при неудаче проверки:
bash 03-cleanup.sh
```

`01-prepare.sh` создаёт тестовые ресурсы; `02-check.sh` выполняет проверки;
`03-cleanup.sh` удаляет только ресурсы этого испытания. Скрипты запускаются независимо.
Повторный полный прогон выполняйте после очистки.

Общие условия и ограничения версии: [README комплекта](../README.md).
