# Пункт 36

Система предоставляет возможность контролировать неавторизованные попытки изменения
политик и авторизацию таких изменений (политики RBAC for Kubernetes, политики СЗИ).

## Что показывает этот пункт

**Результат пункта 36 — записи контроля и авторизации в аудите:** кто пытался
изменить политику, какой объект, разрешён ли PATCH и каким кодом завершился запрос.
Проверяются два вида объектов: Role и SecurityPolicy.

| Учётная запись | GET тестовых политик | PATCH | Запись аудита |
|---|---|---|---|
| observer | Разрешён | Запрещён | 403, решение forbid |
| editor | Разрешён | Разрешён | 200, решение allow |

`kubectl patch` предварительно читает объект. Поэтому observer получает **get**
только для Role `target` и SecurityPolicy `pmi-36`. Без этого права проверялся бы
отказ GET, а до PATCH команда не дошла бы. Скрипт сначала явно показывает успешное
чтение observer, затем требует отказ именно `cannot patch resource`.

Editor получает get/patch для этих же объектов и get/list ConfigMap в тестовом
namespace. Последние права нужны для разрешённого изменения Role: Kubernetes
отдельно проверяет, не выдаёт ли редактор права, которых у него самого нет.

## Подготовка и запуск

Скрипты выполняются на единственном master-узле с административным kubeconfig,
Bash и jq. Подготовка проверяет готовность `admission-policy-engine` и необходимые
поля SecurityPolicy, создаёт namespace `pmi-36`, две учётные записи и тестовые
политики. SecurityPolicy действует только на этот namespace.

Из каталога `36`:

```bash
bash 01-prepare.sh
bash 02-check.sh
# После сохранения доказательств:
bash 03-cleanup.sh
```

Проверка выполняется в четыре шага:

1. Observer успешно читает обе политики.
2. Две его попытки PATCH получают запрет авторизации.
3. Editor выполняет те же PATCH с разрешёнными правами.
4. Скрипт сам читает `/var/log/kube-audit/audit.log` и проверяет четыре строки
   ожидаемых результатов из таблицы в конце `02-check.sh`.

Для чтения файла при необходимости используется sudo. Можно явно указать
другой источник: `AUDIT_FILE=/путь/к/audit.log bash 02-check.sh`.
Отбираются события текущего тестового namespace по времени его создания,
операции patch, стадии ResponseComplete, имени объекта и группе API.
Вывод содержит auditID, время, пользователя, impersonatedUser, объект, код ответа
и `authorization.k8s.io/decision`. Проверяются фактический инициатор, код и решение.

Политика аудита должна сохранять PATCH обоих видов объектов на уровне не ниже
Metadata. Если записи ещё не попали в файл, можно повторить только проверку.
Повторные PATCH editor сохраняют те же значения. Если запись исключена политикой
аудита или ушла в ротированный файл, проверка не объявляет успех.

## Отличие от пункта 37

В пункте 36 сравниваются **две учётные записи** и автоматически проверяются
записи контроля в аудите. В [пункте 37](../37/README.md) у **одной учётной записи**
отзывается разрешение, после чего проверяются блокировка записи и неизменность
проверяемых полей. Одного сообщения Forbidden для закрытия пункта 36 недостаточно.

После проверки Role допускает get/list, а тестовая SecurityPolicy — hostNetwork;
нагрузок в этом namespace нет. Очистка удаляет только созданные тестовые объекты,
включая ClusterRole/ClusterRoleBinding для observer и editor. Журнал сохраняется.
