# Пункт 48

Системой обеспечивается логирование действий с хранилищем конфигураций (etcd). Имеется возможность выгрузки логов etcd на удаленный syslog сервер

## Что проверит подготовка

`01-prepare.sh` проверит готовность `log-shipper`, поля API для выбора журналов
Pod и отправки в сокет, наличие `Syslog` среди форматов установленной схемы
и наличие Pod etcd с меткой `component=etcd` в `kube-system`.
Если модуль, поля, формат или источники недоступны, маршрут создаваться не будет.
Схемы вручную разбирать не требуется.

## Что подготовить на приёмнике журналов

На сервере РЕД ОС 7.3 уже установлен rsyslog. Ниже показано, как добавить
TCP-приём сообщений на порт 514 и сохранять их в `/var/log/deckhouse-etcd.log`.
После настройки на рабочей машине с kubectl укажите адрес этого сервера:

```bash
export SYSLOG_ADDRESS=имя-приёмника:514
```

Входящие сообщения нужно показать в `/var/log/deckhouse-etcd.log` на самом
приёмнике: наличие маршрута в Kubernetes ещё не подтверждает запись в файл.

Сценарий использует TCP без TLS в тестовой сети. Для защищённого канала нужна
отдельная настройка TLS с доверенным CA по схеме установленного log-shipper;
данный вариант отправки не закрывает требование 75.

## Донастройка rsyslog на РЕД ОС 7.3

### 1. На сервере приёмника: добавить отдельный TCP-вход

Основной `/etc/rsyslog.conf` должен подключать `/etc/rsyslog.d/*.conf` — так
настроена стандартная конфигурация РЕД ОС. Посмотреть подключение файлов,
уже включённые TCP-входы и занятость порта можно командами:

```bash
sudo grep -nE 'IncludeConfig|include\(|imtcp|InputTCP' /etc/rsyslog.conf
sudo grep -nRE 'imtcp|InputTCP|port="514"' /etc/rsyslog.d/
sudo ss -lntp '( sport = :514 )'
```

Строки, начинающиеся с `#`, — комментарии. Пример ниже предназначен для сервера,
где приём TCP/514 ещё не включён. Если `imtcp` уже загружен действующей строкой
`module(load="imtcp")` или `$ModLoad imtcp`, уберите **только строку module**
из нового файла: модуль загружается один раз. Если rsyslog уже принимает TCP/514,
не создавайте второй `input` на том же порту: привяжите существующий вход к
`ruleset="pmi48Remote"`, а в новом файле оставьте определение ruleset.
Это направит **все сообщения существующего входа** в отдельный файл; для общего
приёмника с другими отправителями лучше выделить этому тесту отдельный TCP-порт
и указать тот же порт в `SYSLOG_ADDRESS`.

Создайте файл `/etc/rsyslog.d/40-pmi48-remote.conf`:

```bash
sudo tee /etc/rsyslog.d/40-pmi48-remote.conf > /dev/null <<'RSYSLOG'
# Принимаем сообщения тестового канала и сохраняем в отдельный файл.
module(load="imtcp")

ruleset(name="pmi48Remote") {
  action(type="omfile"
         file="/var/log/deckhouse-etcd.log"
         template="RSYSLOG_FileFormat"
         fileCreateMode="0640")
  stop
}

input(type="imtcp" port="514" ruleset="pmi48Remote")
RSYSLOG
```

`imtcp` принимает TCP syslog, `omfile` пишет сообщения в файл. Вход связан со своим
ruleset: обычные локальные сообщения продолжают обрабатываться штатными правилами.
В отдельный файл попадёт всё, что отправлено на этот TCP-вход; отбор журналов
**только etcd** выполняется на стороне Deckhouse в `ClusterLoggingConfig`.
Файл будет создан rsyslog при первом сообщении. Конфигурация рассчитана на штатный
запуск rsyslog от root; при настроенном сбросе привилегий его пользователь должен
иметь право создать/дописывать этот файл.

### 2. На сервере приёмника: проверить и применить конфигурацию

```bash
if sudo rsyslogd -N1; then
  sudo systemctl restart rsyslog
else
  echo "ОШИБКА: конфигурация rsyslog некорректна. Исправьте указанные ошибки до перезапуска."
  exit 1
fi
sudo systemctl is-active rsyslog
sudo ss -lntp '( sport = :514 )'
```

Ожидается успешное завершение проверки, состояние `active` и слушающий TCP/514
процесс rsyslogd. Если `-N1` сообщает о повторной загрузке imtcp или повторном
описании входа, устраните дублирование, как описано в шаге 1. Ошибки запуска
видны в `sudo journalctl -u rsyslog -n 50 --no-pager`.

### 3. Проверить запись локально, затем с рабочей машины

На сервере приёмника отправьте сообщение именно через TCP и откройте файл:

```bash
logger --tcp --server 127.0.0.1 --port 514 --rfc5424 --tag pmi48 \
  'PMI48_LOCAL: проверка приёмника rsyslog'
sudo tail -F /var/log/deckhouse-etcd.log
```

В файле должна появиться строка с `PMI48_LOCAL`. Оставьте `tail -F` открытым.
На рабочей машине выполните следующую команду, заменив `192.0.2.20` настоящим
IP или DNS-именем приёмника:

```bash
export SYSLOG_HOST=192.0.2.20
export SYSLOG_ADDRESS="$SYSLOG_HOST:514"
TEST_MESSAGE="PMI48_REMOTE_$(date -u +%Y%m%dT%H%M%SZ)"
echo "Ищем на приёмнике маркер: $TEST_MESSAGE"
logger --tcp --server "$SYSLOG_HOST" --port 514 --rfc5424 --tag pmi48 -- "$TEST_MESSAGE"
```

В открытом файле приёмника должен появиться этот маркер. Одна успешная отправка
`logger` ещё не подтверждает запись: проверьте сам файл. После этого из каталога
`48` на рабочей машине запускайте три скрипта испытания с заданным `SYSLOG_ADDRESS`.
В файле должны появиться уже реальные сообщения etcd, совпадающие с источником.
Команда `logger` проверяет приёмник и маршрут с рабочей машины; доставку с узлов
кластера доказывают именно реальные сообщения etcd. Просмотр `tail -F` завершается
сочетанием Ctrl+C. Сеть настраивается отдельно; команды firewall здесь не требуются.

### 4. После испытания

`03-cleanup.sh` удаляет маршрут Deckhouse. Настройку rsyslog можно оставить для
дальнейшего сбора. Если созданный TCP-вход больше не нужен, удалите только новый
файл и примените оставшуюся конфигурацию:

```bash
sudo rm -- /etc/rsyslog.d/40-pmi48-remote.conf
if sudo rsyslogd -N1; then
  sudo systemctl restart rsyslog
else
  echo "ОШИБКА: проверьте оставшуюся конфигурацию rsyslog."
  exit 1
fi
```

Файл `/var/log/deckhouse-etcd.log` сохраняется как доказательство испытания.
Если вы меняли привязку ранее существовавшего входа, сначала восстановите его
прежние настройки, затем удаляйте определение тестового ruleset.

Источники: [rsyslog в РЕД ОС 7.3](https://redos.red-soft.ru/base/redos-7_3/7_3-administation/7_3-events/7_3-rsyslog/),
[отдельные ruleset](https://docs.rsyslog.com/doc/concepts/multi_ruleset.html),
[приём TCP](https://docs.rsyslog.com/doc/configuration/modules/imtcp.html),
[вывод в файл](https://docs.rsyslog.com/doc/configuration/modules/omfile.html).

## Демонстрация и критерий

1. Создайте отдельный маршрут pmi-48-etcd → pmi-48-syslog.
2. Запустите проверку, сопоставьте свежие штатные записи etcd на master-узлах
   с принятыми сообщениями syslog по Pod/узлу, времени и тексту. Учитывайте,
   что сборщик может начать с новых записей и не переслать старый tail.
3. На приёмнике покажите реальный журнал, например `journalctl -u rsyslog --since ...`
   для диагностики сервиса и **`/var/log/deckhouse-etcd.log`**
   для доказательства доставки. Запишите UTC-окно; при отсутствии новых записей
   дождитесь штатного обслуживания etcd, не перезапускайте quorum ради демонстрации.
4. Покажите статус/логи log-shipper без ошибок отправки. Наличие CR маршрута
   не означает фактическую доставку. Сохраните совпадающие записи на обеих сторонах.

**Граница:** эксплуатационный журнал etcd не является полным аудитом чтения/записи
каждого ключа и не содержит достоверной личности конечного пользователя Kubernetes.
Для действий с объектами через API используйте аудит из пункта 34. Прямой доступ
к etcd требует отдельного контроля; если пункт требует полный аудит KV-операций,
он не закрывается пересылкой stdout etcd. Подмена этого доказательства недопустима.

Источник: [ClusterLoggingConfig и ClusterLogDestination](https://deckhouse.io/modules/log-shipper/cr.html).

## Запуск

После задания внешних параметров, если они перечислены выше, из каталога `48`:

```bash
bash 01-prepare.sh
bash 02-check.sh
# После фиксации результатов, в том числе при неудаче проверки:
bash 03-cleanup.sh
```

`01-prepare.sh` создаёт тестовые ресурсы; `02-check.sh` выполняет проверки;
`03-cleanup.sh` удаляет только ресурсы этого испытания. Скрипты запускаются независимо.
Повторный полный прогон выполняйте после очистки.

Общие условия и ограничения версии: [README комплекта](../README.md).
