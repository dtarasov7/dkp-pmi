# Пункт 34

Аудит событий Kubernetes API

## Окружение и источник аудита

По информации владельца стенда в кластере **один master**, скрипты запускаются
непосредственно на нём. Источник — **`/var/log/kube-audit/audit.log`**.
Скрипт `02-check.sh` сам читает этот файл: выгружать журнал, подключаться по SSH
или задавать `AUDIT_FILE` перед обычным запуском не требуется.

Нужны Bash, `kubectl`, `jq` и административный kubeconfig. Если текущий
пользователь не может читать журнал, скрипт вызовет `sudo cat` только для чтения
файла; sudo может запросить пароль. Запускать весь скрипт через sudo не нужно:
`kubectl` использует kubeconfig текущего пользователя.

`01-prepare.sh` проверяет аргументы запуска API-сервера, затем создаёт namespace
`pmi-34`, учётную запись observer и выполняет операции с тестовым ConfigMap.
`02-check.sh` получает время создания этого namespace и выбирает из журнала
только завершённые события `ResponseComplete` для `pmi-34/audit-marker`
за время текущего испытания. Временной фильтр включает обе граничные секунды.
Журнал не загружается целиком в массив: сначала jq отбирает нужные строки,
затем проверка подсчитывает только отобранные события.

Политика аудита должна записывать create/get/patch/delete и отказ 403
на уровне не ниже `Metadata`. Наличие аргументов запуска не гарантирует,
что все эти операции сохраняются: например, политика может исключать чтение.
`kubectl get events` не заменяет журнал аудита API.

## Запуск на master-узле

Из каталога `34`:

```bash
bash 01-prepare.sh
bash 02-check.sh
# После сохранения результатов, в том числе при ошибке проверки:
bash 03-cleanup.sh
```

Если последние события ещё не записались, повторите только `02-check.sh`.
Если требуемых событий по-прежнему нет, проверьте политику аудита и ротацию.
По умолчанию читается текущий `audit.log`; записи, уже перенесённые в архив,
в него не входят. Для полного повторного испытания выполните очистку и подготовку.

Если источник действительно отличается, сохранена возможность указать другой
JSON Lines файл (один исходный объект `audit.k8s.io/Event` в строке):

```bash
AUDIT_FILE=/путь/к/другому/audit.log bash 02-check.sh
```

Тот же фильтр текущего испытания применяется и к явно указанному файлу.
Фактический путь API-сервера виден в `--audit-log-path`, который покажет подготовка.

## Ожидаемый результат

В выводе показаны auditID, время, пользователь, impersonatedUser (учётная запись
при `--as`), verb, objectRef, responseStatus и annotations с решением авторизации.
Для каждой операции create/get/patch/delete найдена успешная запись;
для observer найден get с кодом 403. Отсутствие любого события — ошибка проверки.
Сохраните вывод и выбранные записи как доказательства до очистки.

Очистка удаляет только namespace `pmi-34`; исходный журнал не изменяется.
Проверка использует namespace, поэтому её запускают до `03-cleanup.sh`.

[аудит Kubernetes](https://kubernetes.io/docs/tasks/debug/debug-cluster/audit/).
