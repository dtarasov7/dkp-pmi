# Пункт 64

Платформа должна поддерживать многоарендность, в том числе полную изоляцию арендаторов друг от друга.

## Предпосылки и демонстрация

На стенде уже используются Cilium и Hubble. Сетевые правила NetworkPolicy
обрабатывает Cilium. Отдельно включать сетевые компоненты не требуется:
`02-check.sh` проверит фактическую работу правил — сначала успешный обмен,
затем запрет межарендного обмена с сохранением доступа внутри арендатора.
Если общая политика мешает исходному обмену или разрешает трафик вопреки
тестовому запрету, проверка завершится с ошибкой и покажет проблемный запрос.

Испытание использует namespace (отдельные пространства объектов), RBAC (права
доступа к API) и NetworkPolicy (правила сетевого обмена). Создание окружения
через Deckhouse Project показано в пункте 51.

1. Подготовка создаёт двух арендаторов с одинаковыми именами внутренних объектов.
2. Проверка показывает доступ ServiceAccount к своему ConfigMap и Forbidden к чужому
   в обе стороны; затем разрешённый межарендный HTTP до политик.
3. После применения политик ingress и egress разрешены только внутри арендатора:
   собственный HTTP работает, межарендный получает тайм-аут, HTTP readinessProbe подтверждает готовность обоих nginx.
   Обращение по PodIP исключает зависимость результата от DNS.
4. На Cilium дополнительно покажите POLICY_DENIED в Hubble, как в пункте 53.

Для запрещённого запроса принимается только код завершения curl `28`
(тайм-аут). Текст ошибки выводится, но его язык не влияет на проверку.
Ошибки подключения `7`, HTTP-ошибки `22` и ошибки kubectl/RBAC не засчитываются.
Для каждого арендатора повторяется одна последовательность: запрос к своему
серверу → ожидание тайм-аута к чужому → повторный запрос к своему.
Цикл максимум из десяти попыток нужен только для применения политики Cilium.
`CURL_STATUS` — код запроса; `|| CURL_STATUS=$?` сохраняет ожидаемую ошибку
для последующей проверки. Флаги состояния и дополнительная серия запросов не нужны.

## Критерий и границы полной изоляции

Скрипт доказывает разделение доступа к API и трафика тестовых Pod.
**Полная изоляция арендаторов этим не доказана.** Для закрытия исходного требования
проверьте также принятый профиль угроз и конфигурацию стенда:

- tenant не может изменять namespace labels, NetworkPolicy, RBAC, SecurityPolicy,
  создавать ClusterRoleBinding, выполнять impersonate/bind/escalate;
- PSS restricted запрещает hostNetwork/hostPID/hostPath/privileged и исключает обход CNI;
- ResourceQuota/LimitRange ограничивают ресурсы, PVC и StorageClass не дают доступа
  к чужим томам; проверьте права и политику конкретного CSI;
- разделены доступы к логам, метрикам, UI, Secret и внешним хранилищам;
- учтены общий kernel и control plane: для недоверенных арендаторов может требоваться
  разделение узлов или кластеров согласно согласованной модели угроз.

Для каждой границы выполните попытку от настоящего tenant kubeconfig и сохраните
отказ с причиной. Сервисная учётная запись этого теста намеренно имеет только get
ConfigMap и не заменяет проверку реальных ролей арендатора.

Источники: [многоарендность Kubernetes](https://kubernetes.io/docs/concepts/security/multi-tenancy/),
[NetworkPolicy](https://kubernetes.io/docs/concepts/services-networking/network-policies/).


## Тестовые образы

HTTP-сервер — имеющийся `nginx`, клиент — `redos_sudo` с curl.
Для обоих задано `imagePullPolicy: IfNotPresent`.
Nginx слушает 8080, возвращает `pmi-ok` и запускается от UID 1000 с собственными
конфигурацией, PID и временными файлами в `/tmp/pmi-nginx`.
Утилиты curl/wget внутри nginx не требуются. HTTP readinessProbe проверяет ответ
сервера, а `kubectl wait` проверяет готовность обоих Pod после сетевого отказа.
Запросы клиента используют curl с `--noproxy '*'`, чтобы обращаться прямо
к проверяемому Pod/сервису.

## Запуск

После задания внешних параметров, если они перечислены выше, из каталога `64`:

```bash
bash 01-prepare.sh
bash 02-check.sh
# После фиксации результатов, в том числе при неудаче проверки:
bash 03-cleanup.sh
```

`01-prepare.sh` создаёт тестовые ресурсы; `02-check.sh` выполняет проверки;
`03-cleanup.sh` удаляет только ресурсы этого испытания. Скрипты запускаются независимо.
Повторный полный прогон выполняйте после очистки.

Общие условия и ограничения версии: [README комплекта](../README.md).
