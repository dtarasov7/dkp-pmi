# Пункт 37

Система предоставляет возможность блокировки изменений политик в зависимости
от результатов контроля, указанного в пункте 36.

## Что показывает этот пункт

**Результат пункта 37 — блокировка реального изменения после отзыва разрешения.**
Одна учётная запись editor выполняет операции над Role и SecurityPolicy до и после
изменения её прав. Решение контроля авторизации зависит от действующих RBAC-прав.

| Этап | GET | PATCH | Проверяемый результат |
|---|---|---|---|
| До отзыва права | Разрешён | Разрешён | Поля политик действительно изменились |
| После отзыва права | Разрешён | Запрещён | Ответ cannot patch resource, поля остались прежними |
| Контроль администратором | Разрешён | Разрешён | Исходные значения восстановлены |

Это демонстрация синхронного решения авторизатора Kubernetes. Отзыв разрешения
явно выполняет администратор в скрипте; автоматическая реакция SIEM по накопленным
событиям не подразумевается. Если такое требование предусмотрено отдельно,
для него необходим сценарий с конкретной системой реагирования.

## Подготовка и запуск

Подготовка проверяет `admission-policy-engine` и схему SecurityPolicy, создаёт
namespace `pmi-37`, учётную запись editor и тестовые политики. SecurityPolicy
распространяется только на этот namespace.

Права чтения и изменения предоставлены отдельными привязками:

- RoleBinding `reader` и ClusterRoleBinding `pmi-37-reader` дают только get
  конкретных тестовых политик;
- RoleBinding `editor` и ClusterRoleBinding `pmi-37-editor` дают право изменения.

В ходе проверки удаляются только две привязки editor. Права reader сохраняются,
поэтому предварительный GET внутри `kubectl patch` продолжает работать и отказ
относится именно к PATCH. Дополнительные get/list ConfigMap у editor до отзыва
исключают запрет повышения привилегий при разрешённом редактировании Role.

Запуск с административным kubeconfig из каталога `37`:

```bash
bash 01-prepare.sh
bash 02-check.sh
# После сохранения доказательств:
bash 03-cleanup.sh
```

Последовательность проверки:

1. Editor добавляет list к Role и устанавливает allowHostNetwork=true.
   Скрипт читает объекты и подтверждает новые значения.
2. Администратор отзывает право изменения, затем editor снова читает обе политики.
3. Попытка editor вернуть Role к get блокируется; значение остаётся get/list.
4. Попытка вернуть allowHostNetwork=false блокируется; значение остаётся true.
5. Администратор выполняет эти изменения успешно, возвращая исходные значения.

Отказ GET, ошибка API или изменение проверяемого поля после отказа — ошибка
испытания. Сохраните ответы Forbidden и пары значений «до/после».
Для повторного полного прогона нужна очистка и подготовка: права editor
к концу проверки отозваны. При ещё не применившемся отзыве прав проверка
завершится с ошибкой, а не объявит блокировку подтверждённой.

## Отличие от пункта 36

[Пункт 36](../36/README.md) проверяет регистрацию попыток и решений авторизации
в аудите для observer и editor. Здесь проверяется действие решения на запись:
тот же editor теряет право изменения, и запрещённый PATCH не меняет поле политики.
Пункт 37 выполняется независимо, в собственном namespace, без запуска пункта 36.

Очистка удаляет созданные Role/RoleBinding вместе с namespace, тестовую SecurityPolicy
и ClusterRole/ClusterRoleBinding reader/editor. Повторное удаление уже отозванной
привязки editor допускается благодаря `--ignore-not-found`.

[SecurityPolicy](https://deckhouse.io/modules/admission-policy-engine/cr.html).
