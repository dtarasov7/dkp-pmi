## Перед запуском на стенде

- Используйте выделенный испытательный кластер, административный kubeconfig,
  Bash и kubectl. Проверки RBAC требуют impersonation; аудит — jq; резервирование —
  установленный Velero; внешние TLS — curl/openssl. Запуск из каталога пункта.
- Сначала проверьте `kubectl config current-context`, `kubectl version` и
  `kubectl -n d8-system get deployment deckhouse -o jsonpath='{.spec.template.spec.containers[*].image}'`.
  Зафиксируйте редакцию по документам поставки/лицензии и фактическую версию **1.73.4**.
- Cilium уже используется, Hubble включён — это исходная конфигурация стенда.
  Фактическое применение NetworkPolicy проверяют сценарии 53 и 64.
- Проверки готовности нужных модулей, наличия используемых полей API, драйвера
  внешних секретов и хранилища Velero включены в соответствующие `01-prepare.sh`.
  Проверки проходят до создания тестовых объектов; при неудаче скрипт сообщает
  причину. Вручную разбирать схемы перед запуском этих сценариев не требуется.
  Готовность модуля определяется по `Module.status.phase=Ready`, а не только
  по наличию CRD: определения ресурсов могут сохраняться после выключения модуля.
- В README каждого пункта указано, что подготовит скрипт и какие внешние данные
  нужно задать оператору: адреса сервисов, сертификаты, выгрузку журнала.
  Публичная документация приведена как справка; применимость полей API проверяется
  на самом стенде. Модули скриптами автоматически не обновляются и не включаются.
- Все имена `pmi-<номер>` и связанные cluster-scoped имена должны быть свободны.
  Очистка предназначена для ресурсов текущего испытания; не запускайте её,
  если этими именами до испытания пользовались другие владельцы.
  Пункты независимы, но один пункт нельзя параллельно выполнять дважды.
- Зеркалируйте `busybox:1.36.1` и `curlimages/curl:8.12.1` в разрешённый registry
  закрытого стенда и замените image в соответствующих скриптах перед запуском.
  Проверки admission/доступности образов действуют и на тестовые Pod.
- Выполняйте prepare → check → сохранение доказательств → cleanup.
  После ошибки check очистку запускайте отдельно; результаты и журналы сохраняйте
  до удаления объектов. Успешный exit скрипта не заменяет шаги осмотра UI/журналов,
  прямо перечисленные в README конкретного пункта.

## Границы заключения

Пункты 48 (полнота аудита etcd), 64 (полная изоляция), 75 (минимум TLS1.3)
содержат требования шире одной технической демонстрации. В описаниях указано,
что действительно проверяется и какие доказательства ещё требуются.
Пункт 56 требует согласованной таблицы замены требований раздела 6.12.

Внешний сервер секретов, syslog-приёмник, сертификаты и сетевые точки доступа
подготавливаются владельцем стенда: адресов и реквизитов нет в исходных данных.
Их реальные ответы проверяются при выполнении испытания, а принятые записи
внешнего аудита/syslog нужно показать на соответствующем сервере.
Рабочие пароли/токены в комплект не включены.

## Проверка комплекта

Статические проверки и их ограничения записаны в `ПРОВЕРКА.md`.
Испытания на DKP не выполнялись: доступный kubeconfig указывает на
`kind-ktop-test`, API 127.0.0.1:35865 отвечает connection refused.
Для прогона требуется kubeconfig доступного испытательного CSE 1.73.4;
пример переключения для одной команды: `KUBECONFIG=/путь/к/cse-kubeconfig bash 01-prepare.sh`.

Основание проверки состояния модулей: [Module](https://deckhouse.io/products/kubernetes-platform/documentation/v1/architecture/module-development/run/).
