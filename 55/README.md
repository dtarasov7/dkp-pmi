# Пункт 55

Платформа предоставляет возможность настройки защищенного доступа к API-серверу кластера по HTTPS с возможностью ограничения доступа по IP-адресам (белый список).

## Предпосылки

Используется **уже настроенная** публикация Kubernetes API по HTTPS с белым списком.
Нужны две рабочие станции с разными исходящими IP: разрешённая и исключённая,
одинаковый тестовый kubeconfig с правом get namespaces, адрес API, доверенный CA.
Учитывайте NAT и trusted proxy: сравниваются адреса, которые видит точка ограничения.

Для публикации через user-authn покажите:

```bash
kubectl get moduleconfig user-authn -o yaml
kubectl -n d8-user-authn get ingress -o yaml
```

Проверьте publishAPI.enabled и publishAPI.whitelistSourceRanges по схеме 1.73,
TLS-сертификат, Ingress и фактические настройки nginx. Для LoadBalancer проверьте
его sourceRanges и подтверждение исполнения ограничений у облачного провайдера.
Список IP для входа в Dex **не заменяет** ограничение самого API.

## Демонстрация

На каждой станции задайте API_HOST, API_PORT и API_CA для одного и того же endpoint.
Покажите TLS-соединение без отключения проверки сертификата:

```bash
openssl s_client -connect "$API_HOST:$API_PORT" -servername "$API_HOST"   -CAfile "$API_CA" -verify_return_error -verify_hostname "$API_HOST" -brief </dev/null
kubectl --kubeconfig="$TEST_KUBECONFIG" --request-timeout=10s get namespaces
```

На разрешённой станции TLS доверен, API отвечает, список namespace получен.
На исключённой — запрос блокируется на точке IP-фильтрации; в её журнале
зафиксируйте фактический client IP, endpoint, время и причину (например,
access forbidden by rule у nginx). При сетевом ACL допустим тайм-аут только
вместе с deny-log/counter соответствующего ACL и подтверждением маршрута.
Затем повторите положительную проверку с разрешённой станции.

## Критерий

Один endpoint и одни учётные данные дают разные результаты именно по IP.
Kubernetes `Forbidden: User ... cannot list` означает RBAC, а 401 — проблему
аутентификации; они не подтверждают белый список. TLS handshake может проходить
до HTTP-фильтра IP — это нормально. Невозможность маршрутизации без deny-доказательства
также не засчитывается. Проверьте отсутствие обхода через доступный извне master:6443.

Три скрипта не требуются: процедура читает существующую конфигурацию и выполняет
запросы с двух сетей, объектов и изменений нет. Если публикация ещё не настроена,
это предварительная задача владельца стенда с учётом адреса административного доступа.
